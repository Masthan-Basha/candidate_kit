# REVIEW.md

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` / line 73–74 | MongoDB is never pinged — the endpoint always returns `{"status": "ok"}` even if the database is unreachable. The spec says: "Returns 200 only if MongoDB answers a ping, otherwise 503." | Stop MongoDB (`mongod`), call `GET /health` → still gets 200 instead of 503. | Added `client.admin.command("ping")` inside a try/except; returns 503 on failure. |
| 2 | `create_employee()` / lines 79–80 | Uses a check-then-insert (`find_one` → `insert_one`) which has a race condition. Two concurrent requests with the same `emp_code` can both pass the `find_one` check and both insert, violating the uniqueness constraint. The spec says: "concurrent duplicate creates must yield exactly one 201 and the rest 409." | Send two simultaneous `POST /employees` with the same `emp_code`. | Removed the pre-check; wrapped `insert_one` in a try/except for `DuplicateKeyError` (backed by a unique index on `emp_code`). |
| 3 | `list_employees()` / line 93 | `skip = page * page_size` computes the wrong offset. For `page=1` it skips the first page entirely. The correct formula is `(page - 1) * page_size`. | `GET /employees?page=1&page_size=5` returns items 6–10 instead of 1–5. | Changed to `skip = (page - 1) * page_size`. |
| 4 | `list_employees()` / line 94 | `total = db.employees.count_documents({})` always counts all employees, ignoring the `department` filter. The spec says "`total` counts the filtered set, not the whole collection." | Filter by `?department=Sales` when there are 2 Sales employees and 4 total; `total` returns 4 instead of 2. | Changed to `db.employees.count_documents(q)` using the same query object as the find. |
| 5 | `punch_in()` / line 102 | `datetime.fromtimestamp(body.punched_at / 1000)` creates a naive local-time datetime (no timezone). The attendance date calculation (`ts.date()`) then depends on the server's local timezone rather than IST, and the stored BSON datetime will be naive (PyMongo stores it as UTC-equivalent only when the datetime is aware). | Run the server on a machine in a non-IST timezone; a midnight punch produces the wrong attendance date. | Used `datetime.fromtimestamp(ms / 1000, tz=timezone.utc).replace(microsecond=0)` to always get an aware UTC datetime. |
| 6 | `punch_in()` / line 103 | `d = ts.date().isoformat()` computes the attendance date as the UTC date of the punch-in. R1 requires the date to be the IST calendar date, with a special rule for overnight shifts. | An employee on the `09:30–18:30` IST shift punches in at 18:30 UTC (00:00 IST next day) → produces yesterday's date instead of today's. | Replaced with `attendance_date(ts, emp["shift_start"], emp["shift_end"])` which applies R1 including the overnight shift rule. |
| 7 | `compute_late_minutes()` / line 36–37 | `minutes = int((punch_in - start).total_seconds() / 60)` uses the punch-in datetime's date to anchor `shift_start`, but `start` is built with `punch_in.replace(...)` — which only works correctly when `punch_in` is a naive local datetime. With aware datetimes this comparison is correct only coincidentally. Additionally, `minutes > 10` should be `minutes > 10` (strictly more than 10 per R2), which is correct, but the grace period boundary is wrong: 09:40:01 should be 10 minutes late (floor of 10.0167 min elapsed since shift start), the code returns `int(10.0167) = 10` — correct — but the condition `minutes > 10` would reject the 09:40:01 case. Actually re-checking: diff from shift start at 09:40:01 is 10 min 1 sec = 10.016 min → `int(10.016) = 10`; `10 > 10` is False → returns 0. But R2 says 09:40:01 → 10 late. | Test: emp shift_start=09:30, punch-in at 09:40:01 IST → should return `late_minutes=10`. Starter returns 0. | Rewrote using `diff_secs // 60` for true floor-minutes, and correct IST-aware `shift_start` anchoring on the attendance date. |
| 8 | `compute_overtime()` / line 47 | `max(0, ...)` means it returns a positive number even when punch-out is *before* `shift_end` (negative diff becomes 0), which is technically correct, but R3 requires the value to be 0 when < 30 minutes — the `max(0, ...)` skips that threshold entirely. | Employee punches out 15 min after shift_end → function returns 15 instead of 0 (R3: must be ≥ 30). | Rewrote: compute floor-minutes, return value only if `>= 30`, else return 0. |
| 9 | `punch_in()` / line 119 | `doc["id"] = str(res.inserted_id)` adds a spurious `id` field to the response. The spec (openapi.yaml) defines `AttendanceRecord` with no `id` field; `_id` is internal and must never appear in a response. | Call `POST /attendance/punch-in`; response contains `"id": "..."` which the contract forbids. | Removed; only `doc.pop("_id", None)` is kept. |
| 10 | `list_attendance()` / lines 144–146 | Loads the entire `attendance_logs` collection into Python memory (`list(db.attendance_logs.find(q))`), sorts in Python, and computes total as `len(docs)`. This is O(N) in both memory and CPU and will be extremely slow at 100,000 records. The spec says "Must stay fast on a collection of ~100,000 records; do not load the collection into memory." | Run with 100k records and observe memory/latency. | Used `count_documents(q)` for total, applied `.sort().skip().limit()` in MongoDB, and only materialised the requested page. |

## Things examined and decided NOT defects

- **`IST = timezone(timedelta(hours=5, minutes=30))`** — correct UTC+05:30 definition.
- **`load_dotenv()` at module level** — acceptable; reads `.env` before any FastAPI call.
- **`body.model_dump()`** — correct Pydantic v2 API.
- **`shift_start` / `shift_end` defaults `"09:30"` / `"18:30"`** — match the contract.
